# รวม A และ B ใน infra เดียว: แกนร่วม สองช่องทาง และกำแพงกั้นข้อมูล

29 กันยายน 2569 · ต่อจาก [สำรวจโอกาส](onchain-data-infra-scan.md) และ [โมเดลต่างประเทศ](foreign-models-workflows.md) · เอกสารออกแบบเชิงแนวคิด ยังไม่สร้างระบบ

- **A** = ผู้ใช้ยินยอมส่งต่อข้อมูลสินทรัพย์ดิจิทัลและกระเป๋าของตัวเอง ("Your Data สำหรับออนเชน")
- **B** = CFR Pro Max เชื่อมข้อมูลธนาคาร–Exchange–เชน เพื่อตรวจทุจริตก่อนถอน

---

## 1. คำตอบสั้น

**อัปเดตหลัง validation รอบ 2:** ทั้งสองทางมีส่วนประกอบที่อาจใช้ร่วมกัน แต่ยังไม่มีหลักฐานพอเลือก infra หรือฐานข้อมูลเดียว ดู [คำตัดสินและสามทางเลือก](validation-decision-round2.md) ก่อนใช้ข้ออนุมานเดิมด้านล่าง เก็บ [ฉบับก่อนแก้](history/before-validation-round2-2026-09-29/unified-infra-a-b.md) ไว้เทียบแล้ว

ส่วนที่ควรประเมินการใช้ซ้ำมีสามกลุ่ม:

1. **ผูกตัวตนกับบัญชีและกระเป๋า** ให้รู้ว่าบัญชีธนาคาร บัญชี Exchange และกระเป๋านี้เป็นของคนเดียวกัน
2. **มาตรฐานข้อมูลร่วม** ใช้นิยามยอด ธุรกรรม และคำขอถอนแบบเดียวกัน
3. **บันทึกว่าใครเห็นอะไร ด้วยสิทธิอะไร**

แต่ต้องแยก **สองช่องทางที่ฐานสิทธิต่างกัน** และกั้นไม่ให้ข้อมูลไหลข้ามกันโดยอัตโนมัติ

| | ช่องทาง A (ยินยอม) | ช่องทาง B (หน้าที่ตามกฎหมาย) |
|---|---|---|
| ฐานสิทธิ | ผู้ใช้ยินยอมเป็นรายครั้ง ตามวัตถุประสงค์ที่แจ้ง | หน้าที่แลกข้อมูลและระงับธุรกรรมตาม พ.ร.ก. และเกณฑ์ ธปท./ก.ล.ต. |
| ใครเริ่ม | ผู้ใช้ | ระบบตรวจ / การแจ้งเหตุ |
| ผู้ใช้ปลายทาง | ผู้ให้สินเชื่อ ผู้ให้บริการ | Exchange ธนาคาร หน่วยงาน |
| ผู้ใช้เห็นไหม | เห็นและควบคุมได้ | ไม่ได้บอกล่วงหน้า (เพื่อไม่ให้คนร้ายรู้ตัว) |

**กฎกำแพงกั้น [ข้อเสนอออกแบบ]**

- ข้อมูลหรือสัญญาณความเสี่ยงจาก B **ห้าม** ไหลไปช่องทาง A เช่น ห้ามใช้สถานะ "เคยถูกทบทวน" มาตัดสินสินเชื่อ เพราะคนสุจริตจำนวนมากถูกทบทวนผิด
- ข้อมูลที่ผู้ใช้ยินยอมให้ในช่องทาง A **ห้าม** นำไปใช้ใน B โดยไม่มีฐานสิทธิแยก
- หลักจำกัดการใช้ตามวัตถุประสงค์ของกฎหมายคุ้มครองข้อมูลส่วนบุคคลต้องตรวจกับผู้เชี่ยวชาญก่อน เอกสารนี้ไม่ใช่ความเห็นทางกฎหมาย

## 3. ทำไมรวมกันแล้วดีกว่าแยก [อนุมาน]

| ประโยชน์ | เหตุผล |
|---|---|
| **ต้นทุนเชื่อมครั้งเดียว** | Exchange ต่อแกนร่วมครั้งเดียว ใช้ได้ทั้งสองช่องทาง และแกนนี้ต้องทำอยู่แล้วเพื่อ Travel Rule (ยืนยันกระเป๋าตั้งแต่ ก.พ. 2570) |
| **แรงผลักสองทาง** | B มีแรงบังคับจากกฎ (ไม้เรียว) ส่วน A ให้ผลประโยชน์ที่ผู้ใช้และ Exchange อยากได้ เช่น ลูกค้าใช้สินทรัพย์ขอสินเชื่อได้ (แครอท) ถ้ามีแค่ B, Exchange จะมองเป็นต้นทุน compliance ล้วน |
| **คุณภาพการผูกบัญชีดีขึ้น** | ผู้ใช้ที่พิสูจน์กระเป๋าผ่าน A ทำให้ข้อมูลผูกตัวตนแม่นขึ้น แต่ B ใช้ได้เฉพาะเมื่อมีฐานสิทธิ |
| **เล่าเรื่องได้ครบ** | "infra ที่ทำให้สินทรัพย์ออนเชนใช้ประโยชน์ได้อย่างปลอดภัย" ครอบคลุมทั้งโอกาสและความเสี่ยง |

## 4. ความเสี่ยงของการรวม

| ความเสี่ยง | ผลกระทบ | วิธีลด |
|---|---|---|
| **ขอบเขตกว้างเกินไปสำหรับการพิสูจน์** | ไม่มีอะไรพิสูจน์ได้จริงสักอย่าง | พิสูจน์ทีละช่องทาง โดยแกนร่วมเป็นสิ่งเดียวที่สร้างครั้งแรก |
| **ผู้ใช้กลัวว่าข้อมูลที่ยินยอมจะถูกใช้จับผิด** | A ไม่มีคนใช้ | กำแพงกั้นต้องเขียนเป็นกติกาและตรวจสอบได้ |
| **เจ้าภาพต่างกัน** | A น่าจะเป็น ธปท./ก.ล.ต. (Your Data); B เป็น CFR/4 ระบบกลาง | เสนอแกนร่วมเป็นมาตรฐาน ให้แต่ละเจ้าภาพต่อช่องทางของตัวเอง |
| **ความสับสนตอน pitch** | กรรมการไม่รู้ว่าเราแก้ปัญหาอะไร | นำด้วยช่องทางเดียว แล้วโชว์ว่าแกนร่วมรองรับอีกช่องทาง |

## 5. นำด้วยช่องทางไหน

| เงื่อนไข | นำด้วย | เหตุผล |
|---|---|---|
| แข่ง **Track 2** (Linking Chance for All) | **A** | โจทย์ Track 2 ระบุ pain point "การเชื่อมโยงข้อมูลทางการเงินที่กระจัดกระจาย" และวัดผลด้าน Access/Cost/Speed/Inclusion ซึ่ง A ตอบตรง [เอกสารโจทย์บูตแคมป์] |
| แข่ง **Track 1** (Zero Scam Shield) | **B** | ตรงตัวอย่าง "Cross-Bank Fraud Detection Network" |
| เสนอระยะยาวต่อผู้กำกับดูแล | แกนร่วมก่อน | เป็นส่วนที่ใช้ร่วมกับ Travel Rule และ 4 ระบบกลางได้ |

**อัปเดตข้อสังเกต:** ความตรงธีม Track 2 ไม่พิสูจน์ความต้องการสินเชื่อหรือ inclusion ถอนตัวเลขบัญชี active จากเหตุผลจัดอันดับ เพราะยังยืนยันตารางต้นฉบับไม่ได้ และบัญชีซื้อขายไม่เท่ากับคนที่ได้รับประโยชน์จาก A ต้องยืนยันสถานะแทร็กและกลุ่มผู้ใช้จริงก่อนใช้ประกอบการตัดสินใจ

## 6. สิ่งที่ต้องพิสูจน์แยกตามชั้น

| ชั้น | ต้องพิสูจน์ | ถ้าไม่ผ่าน |
|---|---|---|
| แกนร่วม | Exchange ยอมใช้การพิสูจน์กระเป๋าและ data dictionary ร่วมกัน แทนการทำแยก | เหลือเป็นมาตรฐานเสนอ ไม่ใช่ infra |
| A | ผู้ให้สินเชื่อตัดสินใจต่างไปเมื่อเห็นข้อมูลนี้ และผู้ใช้ยอมแชร์ | ตัด A คงแกนร่วม + B |
| B | gate ข้อมูล/การดำเนินการ/ส่วนเพิ่ม ใน `cfr-pro-max-round4-synthesis.md` | ตัด B หรือเปลี่ยนเป็นงานติดตามหลังเหตุ |
| กำแพงกั้น | ได้ความเห็นทางกฎหมายว่าแยกฐานสิทธิแบบนี้ได้ | ต้องแยกเป็นสองระบบ |

## 7. คำถามแรกที่ควรถาม (ยังไม่ได้ติดต่อ)

1. **ถามฝ่ายสินเชื่อธนาคาร/non-bank:** ถ้าลูกค้าแสดงยอดสินทรัพย์ดิจิทัลที่ยืนยันได้จาก Exchange ที่มีกำกับ จะนำมาพิจารณาไหม และจะลดทอนมูลค่าเท่าไร
2. **ถาม Exchange:** จะทำการยืนยันกระเป๋าสำหรับ Travel Rule เอง ซื้อ หรือยอมใช้มาตรฐานร่วม
3. **ถามผู้เชี่ยวชาญ PDPA/compliance:** แกนร่วมเดียวที่มีสองฐานสิทธิ ต้องแยกการจัดเก็บและการเข้าถึงระดับไหน
