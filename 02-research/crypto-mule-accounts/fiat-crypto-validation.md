# ตรวจแนวคิด CFR Pro Max: เชื่อมข้อมูลเพื่อตรวจความผิดปกติข้ามระบบเร็วขึ้น

ตรวจ 29 กันยายน 2569 · เนื้อหาเพื่อให้ผู้ใช้พิจารณา · [ทะเบียนหลักฐาน](fiat-crypto-evidence.md)

ตรวจต่อ: [ทบทวนแปดสถานการณ์และเงื่อนไขข้อมูลมาทันก่อนถอน](fiat-crypto-paper-review.md) พบหลักฐาน ธปท. เรื่องความล่าช้าการแจ้งเหตุ และยืนยันว่าผู้ให้บริการไทยมีการคัดก่อนถอนแล้ว ต้องพิสูจน์ทั้งเวลาของสัญญาณและส่วนเพิ่มเหนือ baseline ห้ามใช้ผลวิเคราะห์ on-chain ในอนาคตมาสนับสนุนคำอ้างว่ารู้ก่อนถอน

ขอบเขตรอบนี้ตามคำขอผู้ใช้: validate ก่อน เตรียมเนื้อหาสำหรับข้อเสนอ hackathon เดโม และ pitch แต่ยังไม่สร้างแอป เดโม สไลด์ หรือเชื่อมระบบจริง ไม่ได้ติดต่อองค์กรหรือรับข้อมูลลูกค้า

## คำตัดสิน

**ปัญหามีหลักฐานชัด แนวคิดเชื่อมข้อมูลมีความเป็นไปได้แบบมีเงื่อนไข แต่ความใหม่ ความจำเป็นใน workflow ไทย และผลเพิ่มจากระบบเดิมยังไม่ผ่านการพิสูจน์**

ควรเดินหน้าตรวจโจทย์นี้ต่อ ไม่ควรนำเรื่องเดิมไป pitch ว่าโลกยังไม่มีเครื่องมือเชื่อม fiat–crypto หรือว่าทำสำเร็จแล้วครึ่งหนึ่ง คำว่า “ครึ่งหนึ่ง” ไม่ใช่สัดส่วนงาน ต้นทุน หรือผลสำเร็จที่วัดได้

ผู้ใช้ชี้แจงกรอบเมื่อ 29 ก.ย. 2569: ข้อมูลอาจมีเพียงพออยู่แล้ว แต่การเชื่อมและวิเคราะห์ร่วมกันอย่างเป็นระบบอาจทำให้ตรวจพบความผิดปกติเร็วขึ้น ใช้ชื่อแนวคิดว่า “CFR Pro Max” ไม่ได้หมายถึงผลิตภัณฑ์ทางการหรือได้รับการรับรองจากผู้ดำเนิน CFR

โอกาสที่เสนอให้พิสูจน์จึงเป็นทั้ง **การสร้างสัญญาณจากความสัมพันธ์ที่แต่ละหน่วยงานมองไม่ครบ** และการส่งหลักฐานให้ผู้มีอำนาจดำเนินการทันเวลา ไม่จำกัดอยู่แค่การส่งต่อ alert ที่ตรวจพบแล้ว ทั้งสามส่วนยังอยู่: กราฟข้ามธนาคาร → การเชื่อมกับรายการภายใน Exchange → การวิเคราะห์ความสัมพันธ์บนเชน

การขาดข้อมูลใหม่ไม่ใช่เงื่อนไขจำเป็นของโอกาสนี้ ข้อมูลเดิมอาจเพียงพอแต่การจับคู่ เวลาเข้าถึง หรือการวิเคราะห์ร่วมยังทำให้รู้ช้า อย่างไรก็ตาม ยังไม่ได้ยืนยันว่า CFR/ระบบที่ติดตั้งจริงขาดความสามารถดังกล่าว ต้องเทียบกับระบบเดิมตามจริง

### ตัวอย่างอธิบายสมมติฐาน

ธนาคารแต่ละแห่งเห็นเงินเข้าบัญชีแล้วโอนไป Exchange ส่วน Exchange เห็นลูกค้าหลายคนฝากและขอถอน ขณะที่ข้อมูลปลายทางบางส่วนมีอยู่บนเชน เมื่อเชื่อมกันอาจเห็นรูปแบบรับ–ส่งเงินที่สอดคล้องกันข้ามหลายบัญชี ซึ่งไม่เด่นชัดเมื่อดูทีละบัญชี ทั้งหมดเป็นตัวอย่างสมมติ ไม่ใช่คำอธิบายสิ่งที่ระบบขององค์กรใดมองไม่เห็นจริง และปลายทางร่วมอย่างเดียวไม่ยืนยันอาชญากรรม

ผลที่ต้องพิสูจน์: ใช้ข้อมูลชุดเดียวกันตามเวลาเดียวกันแล้ว การวิเคราะห์ร่วมพบเคสที่ยืนยันภายหลังได้เร็วหรือครอบคลุมขึ้นเพียงใด ที่ระดับการเตือนผิดและภาระเจ้าหน้าที่เทียบกันได้

## 2. ของเดิมที่ต้องเทียบ

| ของเดิม | สิ่งที่มีหลักฐานว่าทำได้ | งานเราต้องพิสูจน์เพิ่ม |
|---|---|---|
| MITS / เครื่องมือตรวจเครือข่ายฝั่งธนาคาร | เชื่อมความเสี่ยงข้ามสถาบัน [S06] | คุณภาพข้อมูลและการต่อถึง deposit/withdrawal ของ Exchange ไทย |
| CFR และมาตรการไทย | กลไกส่งต่อข้อมูลบัญชี/ธุรกรรมเสี่ยงตามแหล่งทางการ [S07] | ปัจจุบันส่งอะไรถึงใครและทันแค่ไหน ไม่ตั้งสมมติฐานว่า CFR เป็นเพียง blacklist |
| Chainalysis / Alterya | ประกาศ OKX ระบุเชื่อมสัญญาณกับ bank accounts และ crypto wallets และคัดก่อนถอน [S08] | ข้อมูลต้นทางข้ามธนาคารไทยที่ผู้ใช้ยังไม่ได้รับ และผลเพิ่มเหนือระบบที่ติดตั้งจริง |
| เครื่องมือที่ Bitkub ใช้ | ผู้บริหารระบุใช้ Chainalysis และอยากเติมบริบทคัด alert [S09] | เป็นเบาะแส ไม่พิสูจน์ว่าปัญหายังเหลือหลังฟีเจอร์ปี 2569 |
| Travel Rule | ส่งข้อมูลผู้โอน/ผู้รับตามกรอบที่เกี่ยวข้อง [S04] | ไม่ถือว่าการส่งชื่อผู้โอน/ผู้รับเท่ากับส่งเส้นทางเงินหลายทอดพร้อมเหตุผลความเสี่ยง; ต้องเทียบ field จริง |

ไม่ใช้หน้าเว็บผู้ขายพิสูจน์ accuracy หรือ ROI และไม่ใช้การค้นไม่พบฟีเจอร์พิสูจน์ว่าไม่มีใครทำ

## 3. Problem statement และข้อเสนอ hackathon ฉบับตรวจสอบได้

**ผู้ใช้เป้าหมาย:** เจ้าหน้าที่ fraud/compliance ของธนาคารและ Exchange ที่ร่วมโครงการ โดยผู้ตัดสินใจตรวจถอนของ Exchange เป็นจุดใช้งานหลัก

**ปัญหาที่ตั้งสมมติฐาน:** แม้แต่ละหน่วยงานมีข้อมูลธุรกรรมและระบบตรวจของตนอยู่แล้ว ความสัมพันธ์ระหว่างบัญชีธนาคาร ลูกค้า Exchange และปลายทางคริปโตอาจยังไม่ถูกเชื่อมและวิเคราะห์ร่วมกันทันเวลา ทำให้ความผิดปกติระดับเครือข่ายถูกพบช้ากว่าที่ข้อมูลเดิมเปิดโอกาสให้พบได้

**ข้อเสนอ:** เชื่อมข้อมูลที่มีสิทธิใช้ให้เทียบกันได้ทั้งบัญชี ธุรกรรม และเวลา วิเคราะห์รูปแบบข้ามสถาบันและข้าม fiat–crypto อย่างต่อเนื่อง แล้วส่งสัญญาณพร้อมหลักฐาน ความเชื่อมั่น และผู้รับดำเนินการ การประสานข้อมูลอาจเป็นแบบรวมศูนย์หรือแลกผล/ข้อมูลเฉพาะที่จำเป็น ขึ้นกับสิทธิและสถาปัตยกรรมจริง ไม่จำเป็นต้องคัดลอกข้อมูลลูกค้าทั้งหมดมาไว้ที่เดียว

**คุณค่าที่คาดหวัง:** ลดเวลาตั้งแต่มีข้อมูลพอจนตรวจพบเครือข่าย เพิ่มโอกาสดำเนินการก่อนเงินออกจากจุดที่ควบคุมได้ และลดภาระเชื่อมข้อมูลด้วยมือ โดยไม่เพิ่มการรบกวนผู้สุจริตเกินเกณฑ์ที่คู่ทดลองยอมรับ การตรวจพบ การดำเนินการ และการลดความเสียหายต้องวัดแยกกัน

**ผู้ซื้อที่เป็นสมมติฐาน:** Exchange, ธนาคาร หรือผู้ดำเนินโครงสร้างพื้นฐานร่วม ไม่มีผู้ซื้อ งบ การเข้าถึงข้อมูล หรือ partner ยืนยันแล้ว

## 4. ความเป็นไปได้เชิงเทคโนโลยี

```text
รายการข้ามธนาคาร + สัญญาณจากระบบที่อนุญาต
                     ↓
กราฟเส้นทางเงิน พร้อมแหล่งหลักฐานและเวลา
                     ↓
จับคู่ payment reference ↔ deposit record ใน Exchange
                     ↓
Exchange ledger: customer ↔ trade ↔ withdrawal request
                     ↓
ปลายทางถอน + on-chain analytics / ธุรกรรมสาธารณะ
                     ↓
เจ้าหน้าที่พิจารณา → รับเรื่อง/ขอข้อมูล/ดำเนินการ/ปิดเคส
```

ภาพนี้เป็นสถาปัตยกรรมเสนอ ยังไม่มีระบบที่ทำงานแล้ว

### ส่วนที่ 1: กราฟข้ามธนาคาร

ต้องมีรหัสธุรกรรม สถาบันต้นทาง/ปลายทาง account token จำนวนเงิน สกุลเงิน event time และเวลาที่ระบบได้รับข้อมูล เห็นเฉพาะรายการในขอบเขตที่ผู้ร่วมโครงการให้ ไม่สมมติว่า switch เห็นเงินสด on-us ทุกช่องทาง หรือทุกธนาคาร

การรวมและแยกเงินทำให้การอ้างว่า “เงินบาทก้อนนี้กลายเป็น token ก้อนนั้น” ไม่ตรงไปตรงมา ต้องประกาศวิธีจัดสรรยอด เช่น สัดส่วนตามเงินเข้า เป็นสมมติฐานการวิเคราะห์ ไม่ใช่ข้อพิสูจน์ทางกฎหมาย และไม่รวมยอดเดิมซ้ำทุก hop

### ส่วนที่ 2: ส่งต่อหลักฐานธนาคาร–Exchange

ต้องจับคู่ด้วย reference ที่คู่ระบบรับรอง พร้อมเทียบยอด เวลา สกุลเงิน และสถานะ; ใช้ยอด/เวลาใกล้กันอย่างเดียวไม่ได้ ถ้าหลักฐานไม่ครบให้แสดง “ยังเชื่อมไม่ได้” ไม่เติมเส้นเชื่อมเอง

“Risk travels with money” หมายถึงข้อความข้อมูลที่ส่งแยกผ่านช่องทางที่ตกลง ไม่ใช่คะแนนฝังในเงินบาทหรือ USDT และไม่ใช่มาตรฐานที่ติดตามเหรียญไปทั่วโลกได้อัตโนมัติ

ข้อความเสนอให้มี event ID, case ID, transaction reference, ผู้ส่งข้อมูล, เวลาเหตุ/เวลาตรวจพบ/หมดอายุ, เหตุผล, confidence, หลักฐานอ้างอิง, version และสถานะรับเรื่อง ใช้การยืนยันผู้ส่ง การจำกัดสิทธิ การป้องกันรับข้อความซ้ำ และการแก้ไข/ถอนข้อกล่าวหาที่ผิด ข้อมูลอ่อนไหวอยู่กับผู้มีสิทธิ ไม่ส่งรายชื่อลูกค้าทั้งหมดเข้า graph กลางโดยปริยาย

คะแนนความเสี่ยงกับความเชื่อมั่นในการจับคู่ต้องแยกกัน คะแนนสูงแต่จับคู่ลูกค้าไม่ได้ไม่ใช่เหตุผลให้ฟันธงคน และคะแนนจากหลายองค์กรไม่ควรถูกเฉลี่ยรวมโดยไม่มีการปรับเทียบ

### ส่วนที่ 3: กราฟบนเชนและสมมติฐานเครือข่าย

Exchange ใช้กระเป๋ารวมได้ การเห็น hot wallet ส่งออกไม่ได้เปิดเผยลูกค้าภายใน ต้องมี withdrawal record ผูก request/customer กับ transaction hash และ transfer/log index ตาม chain กรณีหลายรายการในธุรกรรมเดียว

การโอนไป Address เดียวกันให้แสดงว่า “มีปลายทางร่วม” ก่อน การระบุว่าเจ้าของเดียวกันหรือแก๊งเดียวกันต้องมีหลักฐานเพิ่ม เพราะปลายทางอาจเป็นบริการรับฝากหรือ payment processor ที่หลายคนใช้ตามปกติ กรณีปลายทางร่วมเป็น service ต้องไม่เหมารวมผู้ใช้ทั้งหมดเป็นเครือข่ายอาชญากรรม

การจัดกลุ่มอาจใช้คุณลักษณะกราฟ เวลา และข้อมูล label ที่ตรวจสอบสิทธิแล้ว แต่ผลต้องแยก observation, inference และ unknown; ไม่ทำคะแนนแบบแพร่ความผิดไปทุก node ที่เคยมีธุรกรรมร่วมกัน

### ขอบเขตการดำเนินการ

จุดแทรกแซงคือก่อน Exchange ปล่อยธุรกรรมถอนเข้าเครือข่าย หลัง broadcast อาจหยุดไม่ทัน ต้องเปลี่ยนเป็นติดตาม/ส่งต่อ ไม่แสดงปุ่ม “อายัด” ที่ควบคุมทุก wallet ได้ และไม่อ้างว่าย้อน blockchain ได้

Offshore platforms และ freeze-resistant assets มีทั้งข้อจำกัดข้อมูล เทคนิค อำนาจ และความร่วมมือ เทคโนโลยีช่วยติดตามบางส่วนได้ แต่การเห็นเส้นทางไม่ได้แปลว่ายึดหรือคืนเงินได้ โจทย์นี้ไม่แก้ข้อจำกัดเหล่านั้นทั้งหมด

## 5. เนื้อหาเดโมที่เสนอ — ยังไม่สร้าง

ใช้ธนาคารสมมติสามแห่ง Exchange สมมติหนึ่งแห่ง และหนึ่งเครือข่ายสาธารณะที่เลือกภายหลัง ตัวเลข เวลา บุคคลและรายการฝั่งธนาคาร/Exchange เป็น synthetic ทั้งหมด

| ฉาก | สิ่งที่กรรมการเห็น | สิ่งที่ต้องพิสูจน์/ข้อจำกัด |
|---|---|---|
| 1. เงินกระจายข้ามธนาคาร | เส้นทางเข้าออกและหลักฐานต้นทาง | ไม่เห็นทุก transaction ของโลก; ยอดไม่ถูกนับซ้ำ |
| 2. ฝากเข้า Exchange | เชื่อม bank reference กับ deposit | แสดงที่มาของ mapping ชัด; ไม่มี mapping ต้องเป็น unknown |
| 3. พบปลายทางร่วม | หลาย withdrawal requests มี destination ร่วม | ให้เป็นเบาะแส; เพิ่มตัวอย่างปลายทางบริการปกติที่ไม่ควรถูกฟันธง |
| 4. ก่อนถอน | เจ้าหน้าที่ได้รับหลักฐานและตอบรับ | วัดว่าข้อมูลมาถึงก่อน release จริงใน simulation ไม่ใช่แค่มีกราฟ |
| 5. ข้อมูลมาช้า/ระบบล่ม | รายการถอนไปแล้วหรือข้อมูลไม่ครบ | แสดง missed intervention และใช้กระบวนการเดิม ไม่รายงานเป็นเงินที่หยุดได้ |
| 6. หลักฐานแก้ไข | ข้อกล่าวหาถูกถอน/ข้อมูลซ้ำ | ไม่สร้างเคสซ้ำและอัปเดตผู้รับเดิม ลดผลเสียจาก false positive |

**ข้อมูล on-chain จริง:** หากสร้างภายหลัง ให้ใช้ตัวอย่างธุรกรรมสาธารณะที่ตรวจ hash, block, chain, token contract, decimals และเวลาบันทึกได้ เก็บ provenance และ snapshot เพื่อ replay ไม่ใช้ตัวเลขสุ่มแล้วเรียกว่า real data ไม่โอนเงินจริงเพื่อทำเดโม

แยกหน้าตัวอย่างข้อมูลสาธารณะจริงออกจากคดีจำลองให้ชัด หากนำธุรกรรมจริงมาประกอบเรื่องจำลองต้องระบุว่า mapping กับธนาคาร/ลูกค้าเป็นสมมติ และไม่ได้กล่าวหาว่าที่อยู่จริงเกี่ยวข้องกับอาชญากรรม ยังไม่ได้เลือกหรือเก็บข้อมูล on-chain สำหรับเดโมในรอบนี้

## 6. วิธี validate ก่อนลงมือ

ตรวจเคสย้อนหลังที่ได้รับสิทธิจากอย่างน้อยหนึ่งคู่ธนาคาร–Exchange เริ่มจากประมาณ 20 เคสเพื่อหาจุดขาดของ workflow ไม่ใช้ขนาดนี้ประมาณผลทั้งตลาด รวมเคสที่ระบบเดิมจับได้ จับไม่ทัน และลูกค้าสุจริตที่ถูกเตือน

คำถามที่ต้องตอบจากงานจริง:

1. ทุกวันนี้ CFR และระบบอื่นส่งข้อมูลชนิดใดถึง Exchange แล้ว ใช้เวลาเท่าไร และข้อมูลติดตรงใด?
2. Exchange ผูกเงินฝากกับ withdrawal request ได้แค่ไหนในกรณีเงินปน ยอดคงเหลือเดิม fee และหลายสินทรัพย์?
3. สัญญาณเกิดก่อนปล่อยถอนหรือเพิ่งเกิดหลังมีการแจ้งความ? หากหลังเสมอ ข้อเสนอ “หยุดก่อนถอน” ใช้ไม่ได้ในเคสเหล่านั้น
4. เครื่องมือ/การตั้งค่าที่มีอยู่เติมข้อมูลนี้ได้อยู่แล้วหรือไม่ และขาดเพราะสิทธิข้อมูล กระบวนการ หรือเทคโนโลยี?
5. ใครมีอำนาจตัดสิน ใครรับผิดชอบ false positive และใครยอมให้ทดลอง/จ่ายค่าเชื่อมระบบ?

การขอข้อมูลหรือสัมภาษณ์ยังไม่ได้ดำเนินการในรอบนี้

### Baseline ที่ยุติธรรม

เทียบกระบวนการปัจจุบันที่มี CFR/analytics และตั้งค่าอย่างเหมาะสมกับการเพิ่มการเชื่อมข้อมูลและการวิเคราะห์ระดับเครือข่าย ตามสามเงื่อนไข A/B/C ด้านล่าง ใช้ข้อมูลเท่าที่มี ณ เวลานั้น ไม่ให้ระบบใดรู้ label หรือผลสืบสวนอนาคต วัด contribution ของแต่ละส่วนด้วยการถอด bank graph, handoff หรือ on-chain grouping ทีละส่วน

ก่อน benchmark จริงต้องแบ่ง train/tune/test ตามเวลาและเครือข่ายเพื่อไม่ให้บัญชีแก๊งเดียวกันรั่วข้ามชุด; ยึดผลยืนยันจากกระบวนการตรวจสอบ ไม่ใช้คะแนนโมเดลของตนเป็น ground truth

| ตัววัด | วิธีตีความ |
|---|---|
| สัดส่วนเคสที่มีหลักฐานครบก่อนถอน | ตัวชี้วัดจุดประสงค์หลัก ต้องรายงานจำนวนเคสฐานและ coverage |
| เวลา signal available → รับเรื่อง → ตัดสิน | รายงาน p50/p95; แยกเวลาคอมพิวเตอร์กับเวลาคน |
| ความถูกต้องของการเชื่อม deposit/withdrawal | นับทั้งจับคู่ผิด จับคู่ไม่ได้ และที่ถูกต้อง |
| False-positive burden | เวลาคนทบทวน จำนวนผู้สุจริตที่ถูกรบกวน และระยะเวลาที่รอ |
| มูลค่าที่หยุดได้เพิ่มเทียบ baseline | ใช้ยอดไม่ซ้ำและหลักฐาน action; ผลจำลองต้องติดป้าย ผลอายัดไม่เท่ากับเงินคืน |
| ต้นทุนต่อเคส | รวม license/API, integration, operation และ human review |

ไม่มีผลทดสอบหรือเปอร์เซ็นต์ improvement แล้วในรอบนี้ ไม่ตั้งเกณฑ์สากลแบบ 95% accuracy หรือ <20 นาทีโดยไม่มีต้นทุนความผิดพลาดและเวลาหน้างานรองรับ

**เกณฑ์เดินหน้า:** พบตัวอย่างที่ข้อมูลพร้อมก่อนดำเนินการแต่การมองแยกส่วน/จับคู่/วิเคราะห์ร่วมทำให้ตรวจช้า หรือพบหลักฐานที่ควรส่งเพิ่ม มี mapping ที่ตรวจได้ มีองค์กรยอมให้ใช้ข้อมูล และมีผู้ตัดสินใจ/เจ้าของงบ ไม่จำเป็นต้องพบว่าขาดข้อมูลใหม่ การทดสอบต้องแสดงส่วนเพิ่มเหนือ baseline ภายในภาระ false positive ที่คู่ทดลองตกลง

**เกณฑ์หยุดหรือเปลี่ยนโจทย์:** ระบบเดิมเมื่อใช้ข้อมูลและการตั้งค่าที่เหมาะสมตรวจและดำเนินการได้เทียบเท่าแล้ว, ไม่มีทางได้ mapping, ข้อมูลที่จำเป็นเกิดหลังถอนเสมอ, หรือไม่มีผู้รับดำเนินการ การที่ระบบเดิมส่งข้อมูลได้อยู่แล้วเพียงอย่างเดียวยังไม่หักล้างประโยชน์ของการวิเคราะห์ร่วม ต้องวัดผลตรวจพบและดำเนินการด้วย

### การเทียบที่ตรงกับสมมติฐาน CFR Pro Max

ทดสอบบนข้อมูลเดียวกันแบบ replay ตามเวลาจริง แยกสามเงื่อนไข: A ระบบเดิมตามการเข้าถึงและการตั้งค่าที่เหมาะสม; B A + เชื่อม/จัดข้อมูลและส่งให้ทัน โดยยังใช้วิธีตรวจเดิมเท่าที่นำมาเทียบได้; C B + วิธีตรวจรูปแบบระดับเครือข่าย เพื่อแยกคุณค่าการเชื่อมข้อมูลออกจากคุณค่าโมเดลใหม่ หากระบบเดิมมีคุณสมบัติ B/C อยู่แล้วต้องนับรวม baseline ไม่ทำให้ baseline อ่อนลงเพื่อให้เราได้เปรียบ

ตรึงข้อมูลที่มีอยู่ ณ เวลาเดียวกัน ไม่ให้ C เห็นข้อมูลอนาคต วัดเวลาแรกที่ตรวจพบเคสที่ยืนยันได้ สัดส่วนพบก่อนปล่อยเงิน และ false positives/ภาระทบทวนที่เทียบกันได้ พร้อมบันทึกเวลาที่ข้อมูลแต่ละส่วนพร้อมจริง การพบเร็วขึ้นยังไม่ใช่เงินที่หยุดได้จนมีหลักฐานการดำเนินการ

## 8. สถานะส่งมอบและหลักฐานที่ยังขาด

- ตรวจข้ออ้างหลักและแก้ positioning แล้ว มีทะเบียนหลักฐานและข้อจำกัด
- มีเนื้อหาข้อเสนอ สถาปัตยกรรม เรื่องเดโม และลำดับ pitch เพื่อให้ผู้ใช้ตรวจ
- ยังไม่ยืนยัน gap หน้างาน ข้อมูลภายใน ผู้ซื้อ ROI หรือผลป้องกันเงินจริง
- ยังไม่มีแอป เดโม สไลด์ หรือชุดข้อมูล on-chain ของโครงการนี้ตามคำสั่งให้ validate ก่อน
- เป้าหมายทั้งสามชิ้นยังคงอยู่ ขั้นถัดไปต้องอิงความเห็นผู้ใช้ต่อเนื้อหานี้ ไม่เริ่มสร้างโดยอัตโนมัติ
