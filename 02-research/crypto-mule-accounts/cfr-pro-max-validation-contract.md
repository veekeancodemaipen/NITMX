## 1. ข้อปรับจากรายงานรอบ 4

ตรวจ [round4-synthesis](cfr-pro-max-round4-synthesis.md) ส่วน 1–3, 5–9 และตารางงานถัดไปแล้ว พบข้อที่ควรแก้ในแบบพิสูจน์:

| จุด | เหตุผล | ข้อกำหนดฉบับนี้ |
|---|---|---|
| เคส W1/W2 เคยส่งไป K ที่ติดป้ายเสี่ยงแล้ว | เครื่องมือเดิมของ Y อาจเห็นความเสี่ยง K เช่นกัน จึงยังสรุปไม่ได้ว่า Y จะปล่อย | แยกแขน “baseline รู้ K” และ “ไม่รู้ K ณ เวลานั้น” ถ้าเดิมพักได้อยู่แล้ว ไม่นับผลพักเพิ่ม |
| ผู้โอนใหม่ 1–2 ราย “ต่ำกว่าเกณฑ์ที่สมเหตุสมผล” | ไม่มี threshold จริงหรือผลประเมินประกอบ | ใช้คำว่า baseline สมมติเพื่อเล่ากลไกเท่านั้น ไม่อ้างว่าระบบธนาคารจริงพลาด |
| A+ ใช้ข้อมูลร่วมและกฎง่าย แต่ถ้าได้ผลเท่า C ให้ลดเหลือข้อมูล | กฎง่ายอาจวิเคราะห์ความสัมพันธ์ร่วมอยู่แล้ว | A+ ชนะ A แต่ C ไม่ชนะ A+ อาจสนับสนุนแก่นแนวคิดด้วยวิธีที่ง่ายกว่า ไม่ได้หักล้างการวิเคราะห์ร่วม |
| แบบรัฐรวมสถานะ/กราฟแล้ว → ลดเหลือชุดวัดผล | มีคุณสมบัติยังไม่พิสูจน์ผลเทียบกัน | รวมของรัฐ/คู่ค้าใน baseline แล้ววัดส่วนเพิ่มก่อนตัดบทบาท |
| เงินมาจากบัญชีตนเองจึงแยกเหยื่อจากม้าได้ | รูปแบบบัญชีไม่ยืนยันความรู้ เจตนา หรือผู้ควบคุมจริง | แยกสถานะ “ผู้ใช้กำลังเสี่ยง” จากสถานะคดี การจำแนกบทบาทต้องมีบริบทและหลักฐานเพิ่ม |
| ปลายทางบริการร่วม “ห้ามนับเป็นความสัมพันธ์” | ความสัมพันธ์ธุรกรรมมีจริง แต่ไม่เฉพาะเจาะจงต่อการควบคุมร่วม | คงเส้นธุรกรรมไว้ ลดน้ำหนักความสัมพันธ์เชิงผู้ควบคุม และไม่จัดกลุ่มทุกลูกค้าของบริการเป็นเครือข่ายเดียว |
| การจับคู่ต้องมี reference ร่วมเท่านั้น | อาจมี mapping ที่ผู้ให้บริการรับรองด้วยวิธีอื่น; reference เองก็อาจผิด/ใช้ผิดขอบเขต | ระบุวิธี หลักฐาน ความหมาย ขอบเขต และอัตราผิด แยกการผูกบัญชีจากการจับคู่รายการ |
| มี heuristic แล้วห้ามใช้พักทุกกรณี | เกณฑ์ความเสี่ยงกับตัวระบุรายการที่ดำเนินการเป็นคนละเรื่อง | ต้องผูกคำสั่งกับรายการถูกต้อง ส่วนหลักฐานความเสี่ยงใช้ตามนโยบาย/อำนาจของเจ้าของกระบวนการ ไม่ยกระดับ heuristic เป็นข้อยืนยันตัวบุคคล |

การแก้เหล่านี้รักษาการตรวจข้ามธนาคาร–หลาย Exchange–บริบทเชนไว้ และทำให้การพิสูจน์ไม่ตั้งต้นจากชัยชนะที่สมมติไว้

## 2. สมมติฐานหกชั้นและผลที่นับว่าได้คำตอบ

| ชั้น | สิ่งที่มีตอนนี้ | หลักฐานที่ต้องได้ในงานจริง | ถ้าไม่ผ่าน |
|---|---|---|---|
| ข้อมูลมีอยู่ | เอกสารกระบวนการ/API และข่าวการแลกข้อมูล | inventory จากเจ้าของระบบพร้อมตัวอย่างที่อนุญาต | ลดคำกล่าวเรื่อง coverage ตามจริง |
| มีทันเวลา | ยังไม่มีเวลาหน้างาน | timestamp ที่เชื่อถือได้ของเหตุการณ์และการพร้อมใช้ | เคสที่มาช้าไม่นับก่อนถอน |
| จับคู่ได้ | แบบรอยต่อและตัวระบุที่เป็นไปได้ | ตรวจตัวอย่าง mapping ถูก/ผิด/ไม่ทราบแยกช่องทาง | ไม่สร้างเส้นเชื่อมแน่นอนจาก heuristic |
| มีสิทธิใช้ | มีฐานหน้าที่ของผู้ประกอบธุรกิจ แต่ไม่มีสิทธิของทีม | ขอบเขตข้อมูล วัตถุประสงค์ ผู้ประมวลผล และการส่งต่อที่อนุญาต | ยังไม่เข้า replay ข้อมูลจริง |
| แยกความเสี่ยงได้ | เคสและ benign twins บนกระดาษ | ผลเทียบ baseline ด้วย labels ที่เหมาะสม | จำกัดเป็นข้อมูลช่วยทบทวน หรือตัด use case ถ้าไม่คุ้ม |
| ดำเนินการทัน | ยังไม่รู้ช่องทาง/เส้นตายจริง | ยืนยันผู้มีอำนาจและ log รับเรื่อง–ตัดสินใจ–ดำเนินการ | แยกเป็นงานตรวจ/ติดตาม ไม่อ้างป้องกัน |

## 3. ขอบเขตข้อมูลและหน่วยการทำงาน

**หน่วยดำเนินการหลัก:** คำขอถอนหนึ่งรายการของ Exchange ที่ร่วม ไม่ใช่ wallet cluster ทั้งกลุ่ม รายการอื่นในเครือข่ายอาจเป็นบริบท แต่ไม่ถูกพักอัตโนมัติตามกัน

**หน่วยตรวจ:** กลุ่มเหตุการณ์ที่มีหลักฐานความสัมพันธ์ในช่วงเวลาที่ระบุ เช่น เงินเข้าหลายบัญชีผู้รับข้ามธนาคาร → เงินฝากของลูกค้าหลายราย → คำขอถอนที่สัมพันธ์กัน ข้อมูลเชนอาจช่วยอธิบายความสัมพันธ์หรือหักล้างความเฉพาะเจาะจงของปลายทาง

**ข้อจำกัดการระบุที่มาของเงิน:** การผูกเงินฝากเข้าบัญชีลูกค้าได้ ไม่เท่ากับพิสูจน์ว่าเหรียญที่ถอนทุกหน่วยมาจากเงินฝากก้อนนั้น เมื่อลูกค้ามียอดเดิม เงินฝากหลายก้อน ซื้อขายหลายครั้ง หรือรวมยอด การจัดสรรแบบ FIFO/สัดส่วนเป็นสมมติฐานทางบัญชีที่ต้องเปิดเผย ไม่ใช่หลักฐานคดีโดยตัวมันเอง ใช้คำว่า “บัญชี/รายการมีความเชื่อมโยงกับบริบทเสี่ยง” จนกว่าเจ้าของข้อมูลและผู้มีอำนาจจะยืนยันการติดตามทรัพย์สินที่เฉพาะเจาะจง

การอ่านเชนสาธารณะและการพิสูจน์ควบคุมกุญแจไม่ยืนยันเจ้าของประโยชน์หรือเจตนาของผู้ใช้ ดูหลักฐานเทคโนโลยี E05 ใน [ทะเบียนเพิ่มเติม](cfr-pro-max-evidence-update.md)

### 3.1 พจนานุกรมข้อมูลขั้นต่ำที่เสนอ

ชื่อด้านล่างเป็นชื่อออกแบบ ไม่ได้อ้างว่าระบบจริงเปิด field เหล่านี้แล้ว ทุกข้อมูลข้ามองค์กรต้องผ่านขอบเขตสิทธิที่ตกลงไว้ ไม่ถือว่า pseudonym เป็นข้อมูลนิรนามโดยอัตโนมัติ

| ข้อมูล | เจ้าของ/เวลาเกิด | วิธีเชื่อมและคุณภาพ | สิทธิ/ผลเมื่อขาด |
|---|---|---|---|
| รหัสองค์กรและรหัสบัญชีภายในขอบเขตงาน | ธนาคาร/Exchange เมื่อสร้างระเบียน | รหัสต้องไม่ชนข้ามองค์กร เก็บหลักฐาน mapping | เจ้าของเก็บการแปลงกลับ; ไม่มี → ห้ามเชื่อมด้วยชื่ออย่างเดียว |
| รหัสเหตุการณ์ เวอร์ชัน และการแก้ไข | เจ้าของเมื่อบันทึกรายการ/แก้ไข | กันรายการซ้ำและตามการถอนข้อมูล | ไม่มี → ไม่รับรองจำนวน/ลำดับและแจ้งคุณภาพ |
| รหัสธุรกรรมธนาคาร ผู้โอน/ผู้รับแบบจำกัดข้อมูล ยอด/สกุลเงิน/สถานะ | ธนาคารเมื่อรายการเกิดและบันทึก | รักษา direction/settlement status ไม่ถือทุก event ว่าเงินเข้าแล้ว | ใช้เฉพาะวัตถุประสงค์ที่อนุญาต; ขาด → เส้นก่อน Exchange ไม่ครบ |
| บริบทประวัติบัญชี/ความสัมพันธ์ผู้โอน | ธนาคาร ณ cutoff | บันทึกวิธีสร้างและช่วงประวัติ ไม่ส่งแค่ alert ที่เกิน threshold | ขาด → ไม่ตีว่าไม่มีประวัติเสี่ยง/เป็นลูกค้าใหม่โดยอัตโนมัติ |
| Deposit ID และ bank reference/mapping ที่รับรอง | Exchange/ธนาคารเมื่อรับและ reconcile | แยก matched/unmatched/disputed พร้อมวิธี ไม่ใช้คะแนนเดียวแทนเหตุผล | ต้องยืนยันสิทธิของ reference ร่วม; ขาด → ไม่อ้าง end-to-end match |
| Customer token และบัญชีธนาคารที่ผูก | Exchange เมื่อยืนยันและเมื่อเปลี่ยน | มีวันเริ่ม/สิ้นสุดและผู้รับรอง ไม่ผูกย้อนก่อนวันที่มีผล | ไม่ส่ง KYC ทั้งแฟ้มโดยไม่มีเหตุจำเป็น |
| การเปลี่ยนยอด/ซื้อขายที่จำเป็นต่อเคส | Exchange เมื่อบันทึก | ใช้ตอบความเชื่อมโยงที่กำหนด ไม่เดา asset flow หนึ่งต่อหนึ่ง | หากไม่มีต้องจำกัดคำกล่าวเรื่องที่มาของยอดถอน |
| Withdrawal ID, ลูกค้า, ยอด, asset, network, destination และ memo/tag เมื่อเกี่ยวข้อง | Exchange เมื่อขอถอน/แก้ปลายทาง | ใช้ identity ของคำขอและเวอร์ชันล่าสุด ไม่ใช้ address ข้ามเชนเป็นตัวเดียวกัน | ต้องเข้าถึงก่อนจุดดำเนินการ; history API อย่างเดียวไม่รับรอง |
| สถานะคำขอ และข้อจำกัดการดำเนินการ | Exchange เมื่อ state เปลี่ยน | เจ้าของตรวจซ้ำ ณ เวลาสั่ง ไม่เชื่อ snapshot เก่า | ขาด → ห้ามอ้างว่าสามารถพักได้ตอนนั้น |
| เหตุผลการพักที่มีอยู่และเจ้าของเหตุผล | Exchange/หน่วยงานที่มีอำนาจเมื่อกำหนด | hold แต่ละเหตุผลแยกกัน ไม่ปลดทั้งหมดเมื่อสัญญาณหนึ่งหมดอายุ | เปิดเผยเฉพาะผู้มีสิทธิ; ขาด → ใช้นโยบายเจ้าของกระบวนการเดิม |
| ประวัติเชนและป้ายปลายทาง | แหล่งเชน/ผู้ให้ข้อมูลตามเวลาที่รู้ | source, chain, observed time, label-created/received time, ความไม่แน่นอน | ขาด → chain contribution = ไม่มี/ไม่ทราบ ไม่เติมป้ายในอนาคต |
| ข้อมูลมาตรการ baseline | เจ้าของระบบเมื่อประเมิน/ดำเนินการ | เวอร์ชันกฎ vendor data และสิ่งที่อนุญาตให้แต่ละแขนเห็น | ขาด → เทียบระบบจริงไม่ได้ |
| ผลรับเรื่อง ทบทวน และดำเนินการ | Exchange เมื่อแต่ละขั้นจบ | signed/authorized record, request ID, outcome/reason; ตรวจการทำซ้ำ | ขาด → รายงานได้เพียงส่งสัญญาณ ไม่ใช่พักสำเร็จ |
| Label สำหรับประเมิน | ผู้ตรวจคดี/คณะ adjudication ภายหลัง | fraud/benign/unknown, แหล่งและวันยืนยัน แยกจาก feature | ขาด → ไม่นับ unknown เป็น benign เพื่อคำนวณ precision |

ทุกแถวต้องมี `เวลาเกิด`, `เวลาพร้อมใช้ของเจ้าของข้อมูล`, `เวลาที่ผู้วิเคราะห์ได้รับ`, `แหล่ง`, `เวอร์ชัน`, `วัตถุประสงค์/สิทธิ` และ `ข้อจำกัด coverage` หากไม่มีเวลา receive จริง ให้ระบุว่า replay ประเมินเวลาโดยสมมติ ไม่อ้างผล latency ที่สังเกตจริง

### 3.2 การลดข้อมูลที่ยังรักษาสมมติฐาน

เลือก feature จากรูปแบบที่จะทดสอบก่อน เช่น จำนวนผู้โอนใหม่ในช่วงเวลา และความสัมพันธ์ข้ามบัญชีที่ได้รับอนุญาต ไม่ตั้งว่า “ส่งเฉพาะ alert” เพียงพอ ต้องเปรียบเทียบว่าการรวมยอด/ลดรายละเอียดทำให้ความสัมพันธ์ที่ต้องการหายไปหรือไม่

ศูนย์กลางอาจเห็นรหัสแทนตัวตนและส่งกลับเฉพาะองค์กรที่เกี่ยวข้อง ส่วนข้อมูลระบุตัวจริงและการตัดสินใจอยู่กับเจ้าของ อีกทางคือประมวลผลบางส่วนที่องค์กรและส่งผลภายใต้กติกาเดียวกัน ทั้งสองทางยังต้องตรวจว่าเหลือข้อมูลพอสำหรับรูปแบบเป้าหมาย ไม่เลือกวิธีเพราะเรียกว่า federated แล้วถือว่าหมดความเสี่ยงข้อมูล

หากมีโครงการช่องทางยินยอม A ควบคู่กับช่องทางป้องกันทุจริต B ให้แยกวัตถุประสงค์ สิทธิ ประวัติการเข้าถึง และการเก็บข้อมูลของแต่ละงาน การใช้ไลบรารีร่วมไม่สร้างสิทธิรวมฐานข้อมูล และผล “ถูกส่งทบทวน” ไม่ควรถูกแปลงเป็นสถานะผิดเพื่อใช้ตัดสินบริการอื่นโดยไม่มีฐานและการตรวจเพิ่มเติม

## 4. เวลาและวงจรการดำเนินการ

นิยาม `T_stop(i)` เป็นเส้นตายอ้างอิงของคำขอ i ตามกระบวนการที่ต้องยืนยันกับ Exchange ไม่ตั้งเท่ากับเวลา block confirmation และไม่ใช้เวลาที่ถูกยืดโดยระบบใหม่มาเป็นเส้นตายให้ตัวเอง

`T_ready` คือเวลาที่ข้อมูลจำเป็นทุกชิ้นเข้าถึงผู้วิเคราะห์ได้; `T_detect` คือสร้างเคส; `T_ack` คือผู้รับตอบรับ; `T_review` คือการตัดสินใจ; `T_action` คือ Exchange ยืนยันผลดำเนินการ ทั้งหมดต้องอยู่บนฐานเวลาที่เทียบกันได้

- `T_detect < T_stop` รองรับ “ตรวจทัน”
- `T_action < T_stop` พร้อมผลดำเนินการที่ยืนยัน รองรับ “ดำเนินการทัน”
- หากไม่รู้ `T_stop` หรือมีเพียงเวลาโดยสมมติ ให้รายงาน “ยังประเมินการทันจริงไม่ได้”
- ถ้า baseline พักรายการอยู่แล้วและไม่มี release counterfactual อย่าแต่งเวลาเดิมที่จะปล่อยขึ้นมา วัดผลทบทวนแยก และรายงานกลุ่มนี้ต่างหาก

| ขั้นที่เสนอ | ผลที่ต้องบันทึก | กรณีผิดปกติ |
|---|---|---|
| สร้างเคส | ความสัมพันธ์ที่เพิ่ม, หลักฐาน, สิ่งที่ไม่รู้, request/version, deadline | ถ้าจับคู่โต้แย้ง ให้ลดข้อสรุปหรือส่งตรวจ mapping |
| ส่งเคส | ผู้รับที่มีสิทธิ, เวลาส่ง/หมดอายุ, source versions | ฟีดขาดต้องแสดง ไม่ถือเป็นความเสี่ยงศูนย์ |
| รับเรื่อง | ack หรือปฏิเสธพร้อมเหตุผล | ไม่มี ack ไม่ถือว่าพักแล้ว |
| ตรวจสถานะและอำนาจ | current state, ผู้ตัดสินใจ, policy version | ถ้าพ้นจุดหยุดได้ ให้ส่งต่องานติดตามตามสิทธิ |
| ตัดสินใจ | review/no new action/ขอข้อมูล/พักตามอำนาจ | การไม่ยกระดับใหม่ไม่ใช่การรับรองว่าปลอดภัย |
| ดำเนินการ | ผลจริงพร้อม timestamp และเหตุผล | คำสั่งซ้ำไม่ทำซ้ำผล และไม่เขียนทับข้อจำกัดจากเหตุอื่น |
| แก้ไข/หมดอายุ | แจ้งทุกผู้รับที่ใช้หลักฐานเดิมและให้เจ้าของทบทวน | TTL/retraction ไม่เป็นคำสั่งปลด hold ทุกกรณี |
| ปิดเคส | เหตุผล ผลต่อผู้ใช้ และ label ที่ทราบ ณ ตอนนั้น | การปล่อยหลังทบทวนไม่เท่ากับ label benign ที่ยืนยันแล้ว |

ระบบต้นแบบในอนาคตต้องทำงานใน shadow mode ก่อนให้มีผลต่อผู้ใช้ ขั้นนั้นยังไม่ได้เริ่มและต้องอยู่ในสิทธิที่อนุญาต

## 5. แผนเปรียบเทียบที่แยกคุณค่าจริง

ใช้ A/A+/B/C1/C2 เดิม และเพิ่ม A+ เร็วขึ้นเพื่อไม่ให้ความต่างของ algorithm ปนกับ latency:

| แขน | ข้อมูล | วิธีตรวจ | เวลา | เปรียบเทียบเพื่ออะไร |
|---|---|---|---|---|
| A | สิ่งที่ระบบจริงเข้าถึง รวม CFR/ผู้ขาย/มาตรการที่ใช้อยู่ | เดิม | ตามจริง | baseline |
| B | เท่ากับ A | เดิม | เร็วขึ้นตามเงื่อนไขที่ทำได้ | B−A: ผลของความเร็วสำหรับวิธีเดิม |
| A+ | A และข้อมูลร่วมที่เพิ่มตามสิทธิ | กฎง่ายซึ่งรับความสัมพันธ์ร่วมได้ | ตามจริง | A+−A: ผลรวมของข้อมูลร่วมกับวิธีใช้ขั้นต่ำ ไม่เรียกว่า data-only |
| A+เร็ว | เท่ากับ A+ | กฎเดียวกับ A+ | เร็วขึ้นแบบเดียวกับ C2 | แยกผลความเร็วในข้อมูลร่วม |
| C1 | เท่ากับ A+ | วิธีวิเคราะห์ที่ซับซ้อนขึ้นถ้ามีเหตุผล | ตามจริง | C1−A+: ส่วนเพิ่มจากวิธีวิเคราะห์เมื่อข้อมูล/เวลาคงเดิม |
| C2 | เท่ากับ A+ | เท่ากับ C1 | เท่ากับ A+เร็ว | C2−A+เร็ว: ส่วนเพิ่มวิธีวิเคราะห์; C2−C1: ผลความเร็ว |

ไม่จำเป็นต้องใช้ AI ถ้ากฎเชิงความสัมพันธ์ง่ายตอบโจทย์ได้ เปรียบเทียบทั้งผลตรวจ ภาระคน และการอธิบายหลักฐาน การย้ายข้อมูลใหม่เข้าระบบเดิมก็เป็นทางเลือกผลิตภัณฑ์ที่ต้องเทียบ ไม่ทำ baseline ให้อ่อนลง

### 5.1 ประชากรและ labels

กำหนดประชากรล่วงหน้าเป็นคำขอถอนในช่วงและช่องทางที่ตกลง รวมรายการจับคู่ไม่ได้และองค์กรที่ข้อมูลหายตาม scope ไม่รายงานเฉพาะกลุ่มที่ข้อมูลสวย

นับผลหลักระดับคำขอถอน และสรุประดับเคส/เครือข่ายเพื่อไม่ให้แก๊งเดียวที่สร้างหลายรายการทำให้ดูเหมือนความมั่นใจสูงกว่าจริง แบ่ง train/tune/test ตามเวลา และตรวจการซ้ำของเครือข่าย หลีกเลี่ยงการใช้ wallet บริการร่วมทำให้ผู้ใช้ทั้งระบบถูกจัดเป็น cluster เดียว

ใช้ labels จากแหล่งยืนยันที่เจ้าของข้อมูลอนุญาต โดยผู้ประเมินไม่ใช้คะแนนโมเดลเป็นเหตุยืนยันความผิด แยก unknown และเคสที่ยังไม่ครบระยะติดตาม การแจ้งเหตุหรือถูกพักไม่ใช่ label fraud โดยลำพัง และการไม่แจ้งเหตุไม่ใช่ label benign

ตรวจ selection bias จากการมี label เฉพาะเคสที่ระบบเดิมเคยเตือน ใช้การตรวจตัวอย่างกลุ่มไม่เตือนตามแผนที่เหมาะสมก่อนอ้าง recall ทั้งประชากร หากทำไม่ได้ ต้องจำกัดขอบเขตข้อสรุป

### 5.2 ป้องกันข้อมูลอนาคตและวัดส่วนเพิ่มของแต่ละชั้น

ใช้ได้เฉพาะ event/label/ความสัมพันธ์ที่ผู้วิเคราะห์รู้แล้ว ณ cutoff; label ยืนยันคดีภายหลังใช้ประเมินเท่านั้น ป้ายเชนที่ถูกแก้ในวันหลังต้องมีประวัติเวอร์ชัน ไม่ใช้ป้ายล่าสุดย้อนหลัง

ทำ ablation โดยนำข้อมูลธนาคารร่วม บริบท Exchange บริบทเชน และความเร็วออกทีละส่วน แล้วรายงานว่าความสามารถลดตรงไหน ถ้าเคสปลายทางใหม่ยังตรวจได้จากธนาคารกับ Exchange ให้ระบุว่าเชนไม่เพิ่มในเคสนั้น ผลรวมไม่ใช่หลักฐานว่าแต่ละชั้นจำเป็นทุกครั้ง

### 5.3 ตัวชี้วัดและเกณฑ์ตัดสิน

| ตัวชี้วัด | นิยามที่ต้องกำหนด | ข้อจำกัด |
|---|---|---|
| Timely detection recall | คำขอที่ label fraud และพบก่อนเส้นตาย / คำขอ fraud ในประชากรที่ประเมินได้ | ขึ้นกับ labels/coverage ต้องแสดง unknown แยก |
| ส่วนเพิ่มสุทธิ | คำขอ fraud ที่วิธีใหม่พบทันแต่ A ไม่พบทัน ลบคำขอ fraud ที่ A พบทันแต่วิธีใหม่ไม่พบทัน | ใช้ประชากร/labels/เส้นตายเดียวกัน ไม่รายงานเฉพาะชัยชนะของวิธีใหม่ |
| Precision ของเคสทบทวน | เคสที่ถูกส่งทบทวนและมี label อิสระยืนยันว่าเกี่ยวข้องกับ fraud / เคสที่ถูกส่งทบทวนและ adjudicate ได้ | ถ้าตัด unknown ออกต้องแสดงจำนวนและความเสี่ยงอคติ ไม่ใช้คะแนนความเสี่ยงยืนยันตัวเอง |
| ความสามารถดำเนินการทัน | มี action ที่ยืนยันก่อนเส้นตาย / คำขอเป้าหมายตาม scope | replay ที่ไม่มีเวลาคนจริงพิสูจน์ข้อนี้ไม่ได้ |
| Coverage และคุณภาพ join | จับคู่ถูก/ผิด/ไม่ทราบ/ไม่มีข้อมูล แยกสถาบัน ช่องทาง เวลา | ไม่ถือ matched ว่า correct |
| ภาระและผลกระทบ | alert, นาทีทบทวน, ขนาดคิว, ลูกค้าสุจริตที่ถูกพักและระยะเวลา | ค่าเฉลี่ยอย่างเดียวซ่อนเคสที่ค้างนาน |
| เศรษฐศาสตร์ | ต้นทุนต่อเคส/รายสถาบันและประโยชน์ผู้ซื้อที่ยืนยันได้ | เงินพัก ≠ เงินที่หลีกเลี่ยงความเสียหาย ≠ เงินคืน ≠ รายได้ผู้ขาย |

**เกณฑ์เสนอ:** ก่อนดูผล กำหนดขนาดผลขั้นต่ำที่คุ้ม (`delta`), ภาระคนสูงสุด, เวลาพักสุจริตสูงสุด, ระดับความผิดพลาดการจับคู่ และวิธีคำนวณช่วงความไม่แน่นอนกับเจ้าของกระบวนการ ไม่เลือกค่าภายหลังเพื่อให้ผ่าน ไม่ให้ตัวเลขสากลโดยไม่มีต้นทุนจริง

ผ่านการตรวจบนกระดาษเมื่อเงื่อนไขเวลา/ข้อมูล/สิทธิไม่ขัดกัน ยังไม่ผ่าน empirical validation จนผลส่วนเพิ่มและผลกระทบอยู่ในเกณฑ์ที่ตกลง ทั้ง statistical significance และขนาดผลที่มีความหมายต่อการทำงานต้องพิจารณา ไม่ใช้ตัวใดตัวหนึ่งแทนอีกตัว

## 6. ผลทบทวนสถานการณ์บนกระดาษ

ตารางนี้เป็นการตรวจตรรกะของข้อเสนอ ไม่ใช่ผลรันระบบ ไม่มีจำนวนเคสจริงหรือเปอร์เซ็นต์ประสิทธิภาพ

| กรณี | ผลที่รองรับได้จากสมมติฐาน | สิ่งที่ห้ามสรุป |
|---|---|---|
| P01 หลายคำขอเกี่ยวข้องกัน และข้อมูลครบก่อนเส้นตาย | สร้างบริบทที่รายองค์กรอาจเห็นไม่ครบ; มีโอกาสส่งทบทวน | ยังไม่ทราบว่าเป็น fraud หรือทบทวนทันจริง |
| P02 baseline รู้ปลายทางเสี่ยงและพักอยู่แล้ว | ไม่มีส่วนเพิ่มเรื่องพักรายการ อาจวัดการยืนยัน/ลดงานแยก | ห้ามนับยอดพักเป็นผลใหม่ |
| P03 ข้อมูลครบหลังเส้นตาย | ใช้ติดตาม/คำขอถัดไปได้ตามสิทธิ | ห้ามนับว่าช่วยรายการแรกทัน |
| P04 ประวัติเชนใหม่ว่าง | ทดสอบเฉพาะข้อมูลธนาคาร–Exchange | ห้ามแต่ง risk label หรือ claim คุณค่าเชน |
| P05 ปลายทางเป็นบริการร่วม | คงเส้นเงิน แต่ความเฉพาะเจาะจงลด | ห้ามสรุปผู้ควบคุมเดียวกัน |
| P06 คนสุจริตมี observables เหมือน P01 | แยกไม่ได้ด้วยข้อมูลชุดเดียวกัน ต้องรับความไม่แน่นอนและต้นทุนทบทวน | ห้ามใช้ AI อธิบายเจตนาที่ไม่ได้สังเกต |
| P07 เงินตนเองแต่ถูกหลอกหรือมีเจตนาร่วม | บทบาทยังไม่ทราบ ต้องมีบริบทที่ได้รับอนุญาต | ห้ามจำแนกเหยื่อ/ม้าจากแหล่งเงินเพียงอย่างเดียว |
| P08 mapping ถูกแก้ | ถอนข้อสรุปที่พึ่งเส้นนั้น แจ้งผู้รับ และประเมินหลักฐานที่เหลือ | ห้ามปลดทุก hold อัตโนมัติ |
| P09 ข้อมูลซ้ำ/ผิดลำดับ | ใช้ version และเวลาได้รับ ป้องกันนับซ้ำ | ห้ามเลื่อนเวลารู้ข้อมูลย้อนหลัง |
| P10 สถานะเปลี่ยนระหว่างส่งกับรับเรื่อง | เจ้าของตรวจ state ปัจจุบันก่อนดำเนินการ | ack ไม่เท่ากับ action |
| P11 ฟีดหนึ่งหายหรือ P2P/offshore ไม่อยู่ใน scope | แจ้ง coverage gap และรักษามาตรการเดิม | ห้ามให้ missing = safe หรือเติมเจ้าของที่เดา |
| P12 A+ ได้ผลเท่า C1 และดีกว่า A | อาจใช้กฎร่วมที่ง่ายกว่าและรักษาแก่นแนวคิด | ห้ามกล่าวว่าการวิเคราะห์ร่วมไม่มีคุณค่าเพราะ AI ไม่ชนะ |
| P13 ระบบกลางมี feature แบบเดียวกัน | ต้องใช้ผล/ต้นทุนของระบบนั้นเป็น baseline | ห้ามลดเหลือชุดวัดผลอัตโนมัติจากชื่อ feature |
| P14 ยอดเดิมปนหลายฝาก/หลาย trade | ใช้ความสัมพันธ์ระดับบัญชีพร้อมขอบเขต attribution | ห้ามอ้างทุกเหรียญถอนเป็นเงินจากธุรกรรมหนึ่งแน่นอน |
| P15 labels มีเฉพาะรายการที่เคยถูกเตือน | ประเมินได้ในกลุ่มที่มี label พร้อมข้อจำกัด | ห้ามอ้าง recall ของทุกคำขอ |
| P16 ลูกค้าได้รับความเสียหายจากพักผิด | นับผลกระทบและเวลาจริงในเกณฑ์คุ้มค่า | ห้ามนับแต่เงินที่พักและซ่อนต้นทุนลูกค้า |

## 7. แผนตัดสินใจหลังมีหลักฐานจริง

1. ถ้ามี mapping/สิทธิ แต่ไม่มีข้อมูลก่อนเส้นตาย → แยกข้อเสนอหลังเหตุ หรือเลือกจุดแทรกแซงก่อนหน้าที่มีสิทธิและมีหลักฐาน ไม่เปลี่ยนชื่อแล้วอ้างว่าป้องกันคำขอเดิมได้
2. ถ้าข้อมูลพร้อมแต่ไม่เพิ่มเหนือ baseline → ลด/หยุด use case นั้น ไม่เพิ่มโมเดลเพื่อรักษาไอเดีย
3. ถ้ากฎร่วมง่ายเพิ่มผลและ C ไม่เพิ่ม → ใช้วิธีง่าย พิจารณาต่อยอดระบบเดิมหรือโมดูลเฉพาะตามต้นทุน
4. ถ้าตรวจเพิ่มแต่คนไม่ทัน → ทดลองกระบวนการรับเรื่องแยกจากการเพิ่มโมเดล ยังไม่อ้างประโยชน์เงินที่ป้องกัน
5. ถ้าผลเพิ่มคุ้มแต่ไม่มีช่องทางซื้อ → เป็นงานวิจัย/โครงการร่วมได้ ยังไม่ผ่านการพิสูจน์ธุรกิจ
6. ถ้าครบข้อมูล เวลา ผลกระทบ และผู้ซื้อ → จึงเสนอขั้นทดลองที่มีขอบเขตและผู้รับผิดชอบ ไม่ข้ามไปใช้งานระดับชาติ

เอกสารนี้ทำข้อกำหนดสำหรับการวิเคราะห์และการหารือพร้อมแล้ว Gate ข้อมูลจริง อำนาจ ผลตรวจ และผู้ซื้อยังไม่ผ่าน การอนุญาตสร้างเดโม/ทดลอง/ติดต่อเป็นขั้นงานถัดไปตามขอบเขตที่ผู้ใช้เลือก
